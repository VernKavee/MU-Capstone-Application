# ควรย้ายโค้ด RAG เข้าแอปเพื่อให้ deploy ง่ายขึ้นไหม

ตรวจจากโค้ดเมื่อ 2026-11-04 แผน deploy ยังไม่เคยซ้อมจริง

## สรุป

เป้าหมายที่อยากให้ deploy เป็นชุดเดียวนั้นสมเหตุสมผล แต่**ไม่จำเป็นต้องย้ายโค้ดเพื่อให้ได้สิ่งนี้** เพราะ `docker compose` ไฟล์เดียว build จากหลาย repo แล้วสั่งขึ้นทั้งระบบด้วยคำสั่งเดียวได้

ข้อเสนอคือแยก repo ไว้ก่อน ใช้ compose ชุดเดียว และระบุรุ่นของ RAG_SYSTEM ให้ชัดเจน ถ้า prompt นิ่งแล้วและทีมยังอยากได้ repo เดียว ค่อยย้ายเฉพาะไฟล์ที่จำเป็นเข้ามา

**ขอให้ช่วยตอบ 1 ข้อ:** "docker ก้อนเดียว" หมายถึงแบบไหน

- **คำสั่งเดียวขึ้นทั้งระบบ:** แนวทางนี้ตอบโจทย์โดยไม่ต้องย้ายโค้ด
- **image เดียวรวมทุกอย่าง:** ไม่แนะนำ (เหตุผลอยู่ในหัวข้อถัดไป)
- **ไม่อยากดูแลสอง repo:** เป็นเหตุผลคนละเรื่องกับการ deploy ควรคุยกันเรื่องการย้ายเฉพาะไฟล์ที่จำเป็น (แบบ B)

## ตอนนี้ระบบต่อกันยังไง

แอปเรียก service ทั้งสองผ่าน HTTP

```text
Next.js ── POST :8765/score ────> similarity (services/similarity/ ในแอป)
        └─ POST :8100/feedback ─> feedback (repo RAG_SYSTEM)
                                    ├─ ค้น KB ใน Postgres ของ Supabase
                                    └─ ให้ Groq หรือ Gemini เขียนคำแนะนำ
```

similarity อยู่ใน repo แอปก็จริง แต่ยังเป็น Python คนละ process และคนละ venv กับ Next.js ดังนั้น**การย้าย RAG เข้ามาจะไม่ทำให้มันรวมเป็น process เดียวกับแอป**

แอปเรียก feedback ผ่าน `FEEDBACK_URL` ใน `lib/analysis/feedback.ts` จึงไม่ต้องสนใจว่าโค้ดของ service เก็บอยู่ที่ไหน

## การย้ายโค้ดเปลี่ยนอะไรบ้าง

| เรื่อง | แยก repo | ย้ายเข้ามา |
|---|---|---|
| จำนวน process หรือ container | Node และ Python แยกกัน | เท่าเดิม |
| การโหลด KB เข้า Postgres | ต้องทำ | ยังต้องทำ เพราะ KB เป็นข้อมูล ไม่ใช่โค้ด |
| การ clone บน VM | 1 หรือ 2 repo แล้วแต่วิธี build | 1 repo |
| ล็อกรุ่นของแอปกับ prompt | ต้องระบุ tag หรือ commit เอง | commit เดียวครอบคลุมทั้งคู่ |

ประโยชน์จริงของการย้ายมี 2 ข้อ

1. Clone บน VM ครั้งเดียว
2. แก้ prompt กับตัวแยกข้อความ (`rag_core/prompt.py` กับ `lib/feedback-text.ts`) ใน commit เดียวกันได้

**ทำไมไม่ทำ image เดียว:** Next.js, torch และ langchain จะอยู่รวมกัน ทำให้แก้หรือ restart ทีละส่วนไม่ได้ และ API key ของ LLM ก็จะอยู่ร่วมกับแอป นอกจากนี้ Supabase เองก็มีหลาย container อยู่แล้ว ระบบจึงไม่มีทางเหลือก้อนเดียวจริงอยู่ดี

## ถ้าจะย้าย ย้ายเฉพาะที่จำเป็นได้ไหม

ได้ RAG_SYSTEM มีไฟล์ใน git 449 ไฟล์ รวม 157 MB แต่ส่วนใหญ่เป็นงานเตรียมข้อมูลและ eval ที่ service ไม่ได้ใช้ตอนรัน

| ประเภท | รายการ |
|---|---|
| โค้ดที่ต้องใช้ (12 ไฟล์ ราว 135 KB) | `service/`, `rag_core/`, `embedding_config.py`, `error_taxonomy.py` |
| ข้อมูลที่ต้องใช้ | `gemini-embedding-2.json` (ใช้ตอนรัน), `kb_dump.sql.gz` (ใช้โหลด KB) |
| ไม่ต้องย้าย | `eval/`, `tools/`, `data/`, `curated_data*`, `data_pipeline/`, `ingest.py` |

**ผลทดสอบ:** แยกโค้ดชุดนี้ไปไว้ในโฟลเดอร์ชั่วคราว แล้ว import service สำเร็จ และ `test_service.py` กับ `test_app_input.py` ผ่านทั้งคู่ การทดสอบนี้ใช้ venv ตัวเต็มของ RAG_SYSTEM และจำลอง DB กับ LLM จึงยังไม่ใช่การรันจริงกับ KB และโมเดล

**เรื่องที่ต้องจัดการถ้าย้าย**

- **commit หาย:** `version.commit` เป็น `unknown` เมื่อไม่มี git และถ้าอยู่ในแอปจะไปอ่าน commit ของแอปแทน จึงต้องเปลี่ยนวิธีระบุรุ่น
- **ต้องซิงก์ทุกครั้ง:** eval ยังอยู่ที่ RAG_SYSTEM จึงต้องก๊อปตรงทุกไบต์และบันทึก commit แบบ `services/similarity/SOURCE.md` ไม่อย่างนั้นผล eval จะไม่ได้บอกอะไรเกี่ยวกับโค้ดที่รันจริง
- **KB dump ใหญ่:** ไฟล์ 34 MB จะเพิ่มประวัติ git ของแอปทุกครั้งที่ commit รุ่นใหม่ จึงควรเก็บไว้นอก repo นี้
- **กติกาทีม:** ต้องแก้ `CLAUDE.md`, ADR-0007 และ `docs/HANDOVER.md` ให้ตรงกับที่อยู่ใหม่

## เปรียบเทียบ 3 ทางเลือก

| | A. แยก repo + compose ชุดเดียว (แนะนำ) | B. ย้ายเฉพาะที่จำเป็น + compose | C. ย้ายทั้ง repo |
|---|---|---|---|
| คำสั่ง deploy | คำสั่งเดียว | คำสั่งเดียว | คำสั่งเดียว |
| ของที่เข้า image | เฉพาะที่ Dockerfile เลือก | เฉพาะที่จำเป็น | เฉพาะที่ Dockerfile เลือก |
| โค้ดที่รันตรงกับที่ eval | ตรง ถ้าระบุ tag | ตรง ถ้าซิงก์ถูก | ตรง แต่ต้องย้ายงาน eval มาด้วย |
| เมื่อแก้ prompt | ขยับ tag | ก๊อปไฟล์ใหม่ทุกครั้ง | แก้ที่เดียว |
| ผลต่อ repo แอป | ไม่เพิ่ม | เพิ่มเล็กน้อย | เพิ่ม 449 ไฟล์, 157 MB |

**ทำไมเลือก A**

- ได้คำสั่งเดียวตามเป้าหมาย โดยไม่ต้องย้ายโค้ด
- prompt ยังเปลี่ยนอยู่ (v14 ถึง v16 ใน 8 วัน และยังมีปัญหาที่แนะนำให้ลดน้ำหนักในท่าที่ไม่ใช้น้ำหนัก) ตอนนี้จึงเป็นช่วงที่การซิงก์ของ B เสียแรงที่สุด
- Dockerfile เลือกไฟล์เองได้ image จึงไม่มีข้อมูล eval ปนไป

**ข้อเสียของ A**

- prompt กับตัวแยกข้อความยังอยู่คนละ repo ถ้าแก้ฝั่งเดียว แอปจะแสดงข้อความทั้งก้อนแทนรายการ fault โดยไม่มี error แจ้ง
- ทีมต้องมีวินัยเรื่องการติด tag และอัปเดต tag ใน compose

**จะเปลี่ยนไปใช้ B เมื่อไหร่:** เมื่อ prompt นิ่งแล้ว และทีมอยากให้ VM ขึ้นจาก repo เดียวจริงๆ ซึ่งย้ายภายหลังได้ง่าย เพราะฝั่งแอปเรียกผ่าน URL อยู่แล้ว เริ่มจาก A จึงไม่ปิดทางเลือกนี้

## หน้าตาของ compose แบบ A

ตัวอย่างนี้เป็นโครงคร่าวๆ ที่ยังไม่ได้ลองรัน โดยเฉพาะการ build จาก git URL ต้องทดสอบตอนซ้อม deploy

```yaml
services:
  app:
    build: .
    environment:
      FEEDBACK_URL: http://feedback:8100/feedback
  similarity:
    build: ./services/similarity
  feedback:
    build: https://github.com/sujira7236212/Capstone_RAG.git#<tag>
```

## งานที่ต้องทำไม่ว่าจะเลือกแบบไหน

- [ ] เขียน Dockerfile ของแอปและ service ทั้งสอง เพราะตอนนี้ยังไม่มีเลย
- [ ] ตั้งค่า host ของทั้งสอง service ใหม่ เพราะตอนนี้ผูกกับ `127.0.0.1` ซึ่ง container อื่นเข้าไม่ถึง และห้ามเปิด port ออกนอก Docker network เพราะ service ไม่มีการยืนยันตัวตน
- [ ] เชื่อม compose นี้เข้ากับ compose ของ Supabase
- [ ] เพิ่มขั้นตอนโหลด KB และคัดลอก query vectors
- [ ] ส่ง `NEXT_PUBLIC_*` เป็น build arg เพราะค่าเหล่านี้ถูกฝังตอน build
- [ ] แก้ `docs/DEPLOY.md` เพราะแผนปัจจุบันให้ Next.js และ Python รันด้วย systemd และยังเขียนถึง feedback ว่า "once it exists"
- [ ] ซ้อม deploy บน VM ทดลองก่อนใช้จริง

## ขั้นตอนถัดไป

1. ตอบคำถามในหัวข้อสรุปว่า "docker ก้อนเดียว" หมายถึงแบบไหน
2. ตกลงกันในทีมว่าจะเปลี่ยนจาก systemd เป็น compose ไหม
3. ลองทำบน VM ทดลอง แล้วค่อยแก้ `docs/DEPLOY.md` ตามผลจริง
