### 1. One workout row, no duplicate sets (`faa347d`)

The database used to hand out the workout id only when the first save worked. Tracing it found
three ways to split or duplicate rows: a failed first save gave the next set a second workout; a
set insert failing after the workout insert left an empty workout; a signing failure after the
set insert saved the set again on retry. The live screen now makes the workout id once and each
set's id at its end (`crypto.randomUUID()`), and `saveSet` inserts both with `on conflict (id) do
nothing`. Checked: pgTAP (saving twice leaves one row; a save naming B's workout writes nothing
and its set is refused), and `saveSet` run against the local stack as a throwaway user: set 1
twice plus set 2 gave 1 workout and 2 sets.

### 2. A retry signs fresh upload URLs (`cd399bf`)

Signed upload URLs last two hours and a retry reused them. A retry with a file still to send now
saves again, which only signs afresh. Unit-tested; an expired URL was not tried.

### 3. Resume after a reload (`489aa4f`)

After the first save the address gets `workout=<id>`. `resumePoint` (`lib/set.ts`) resumes when
the last set ended under five minutes ago, at the highest set number plus one, with the setup
from the workout row; a pending repair set is dropped and no decline written; with every set
saved only Finish is left; otherwise `workout` is dropped and a new workout starts. A scratch
Playwright run with seeded workouts passed all four paths (2 min, all saved, 6 min, malformed).
Not tested: that a real first save writes `workout=`, because Chrome's fake camera (a frontal T
pose) never places the squat at 45 degrees, so no set ends.

### 4. History lists unfinished workouts, twenty to a page (`88d339f`)

Level 3 lists every workout with a saved set (`sets!inner`), a workout left part way marked "Not
finished", with `?before=` paging; the deep dive marks it too. Active days stay finished-only.
Checked with 23 seeded workouts at 375 and 1280 px: 20, then 2, the empty workout hidden.

### 5. The analysis is the server's to write (`3ea263e`)

Migration `analysis_server_only` revokes the update grant on `attempts`, `similarity`, and
`llm_feedback`. `analyseSet` reads with the user's client, which proves ownership, and writes
with `lib/supabase/admin.ts` (`SUPABASE_SERVICE_ROLE_KEY`, added to `.env.local` from the local
stack). Applied with `migration up`, not `db:reset`, so local data stayed. Checked against the
stack: feedback written by the server, the user's own update refused (42501), another user's set
id writes nothing. Limit: the first save still runs in the user's session.

### 6. Replay out of step (`9e81c73`)

Workout `44bd485d`, set 1's repair set: 59.0 s of keypoints, 56.8 s of video; set 1 and set 2
differ by 28 and 13 ms. Replay took the difference as a start delay, clamped to 2 s, so the
skeleton ran 2 s ahead throughout. The files were copied out of the storage container
(`docker cp`, read only) and the video's frame times read from the webm: 30 fps, no gap over
45 ms. The picture's motion (Chrome, frame differences) against the keypoints' motion, in 8 s
windows: lag 50 to 100 ms from start to end in all three sets, correlation 0.75 to 0.91. So no
drift: the recording lost its last 2.2 s, when the keypoint rate had fallen from 35 to 14 fps.
The keypoint file now carries `video_start_ms` from MediaRecorder's `start` event (29 to 95 ms
after `start()` in Chrome); replay uses it, or 0 for older files, and the guess from the video's
length is deleted. The lost seconds themselves stay open. Scratch scripts in the session's
scratchpad (`webm_times.py`, `lag.py`, `pw/motion.check.ts`).
