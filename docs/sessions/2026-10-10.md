# Session 2026-10-10, the first phone run

Vern installed `cloudflared` with Homebrew, and his manager allowed tunnels on his Mac. The
first phone run (iPhone, iOS Safari) went through two Cloudflare quick tunnels from the Mac.
Vern filmed it as a screen recording and reported two bugs. One commit per step.

## The run

- `npx supabase start`. Then `cloudflared tunnel --url http://127.0.0.1:54321` for the API,
  and `npm run build` and `npm start` with `NEXT_PUBLIC_SUPABASE_URL` set to the API
  tunnel's address on the command line. Then `cloudflared tunnel --url
  http://127.0.0.1:3000` for the app. Both tunnels answered over https before the phone
  opened the app.
- On the phone: sign-in, the Home chart, the squat setup and guide, the camera prompt,
  three sets, two set-complete screens with the stub similarity and feedback, and the
  finished summary. History replay was not reached.
- Afterwards the tunnels, the app, and the stack were stopped.

## Findings, from the screen recording (frames pulled with AVFoundation, no ffmpeg here)

1. **No sound.** The phone was on silent, and iOS Safari mutes Web Audio on silent. Vern:
   respect the switch, no change (`navigator.audioSession.type = "playback"` was the
   option). Check with silent off on the next run, beeps and speech separately.
2. **The video shrinks when the set goes active (112s).** It drops to a centred 240 x 427
   CSS px box, which is 720 x 1280 / 3: the camera's native pixels at the phone's pixel
   ratio. So WebKit stops applying `object-fit: cover` to the video once MediaRecorder
   starts on the camera track. The skeleton canvas, with the same class and sized to the
   video, stayed full screen and fitted, with the skeleton overflowing the small box.
3. **Set 1 ended with 0 attempts, "You ended the set".** Vern held the T pose too far back.
   The countdown started, ran out, and held at 0 on "Move closer to the camera". When he
   came forward and turned, the set started without him noticing, and he held the T pose
   again (112.5s to 114.5s, about 2 s at 42 fps). That is the designed end of a set, so his
   second T pose ended it. Vern: the distance has to be right before the T pose counts.

Also seen, not fixed: the frame rate shown in the HUD was 42 to 48 fps up to and into set
1, then 8 to 27 fps from set 2 on, already during set 2's countdown, so it is not simply
the recorder starting. Cause unknown (heat, the uploads, the encoder). Watch it on the next
run: the engine's holds and debounces count frames.
